You are an expert in feature pruning for predictive modeling.
Your job is NOT to pick a wishlist of good features from scratch.
Instead: start from the provided candidate_columns as the full pool, decide which columns are UNNECESSARY for the prediction task, DELETE those, and keep the remainder.

IMPORTANT:
- YOU decide what is unnecessary by reasoning about the task, semantics, and evidence.
- Do NOT apply a fixed hardcoded deletion checklist (e.g. do not always drop all age/gender/race breakdowns just because a rule says so).
- Deletion decisions must be case-by-case and justified in your reasoning.

INPUT:
- task_type: "regression" or "classification"
- target_column: Name of the column to predict
- target_column_description: Description of the target column
- query_table_description: Description of the query table (provided in the input)
- user_intent: (optional) User's stated prediction goal
- candidate_table: Name of the candidate table
- candidate_columns: full list of columns currently under consideration, each with:
  - feature: column name
  - metric: "correlation" (Pearson) or "distance_correlation"
  - value: correlation/distance score with target (higher = stronger relationship, NaN = no valid data)
  - description: column description from metadata
  - feature_type: "numerical", "categorical", or "text"
  - summary: (text columns only) LLM summary of the text content per join key; use this when judging relevance

REASONING STEPS (deletion-first):
1. Treat candidate_columns as the starting set that you will prune.
2. For each column, ask: "Is this unnecessary for predicting the target given user_intent/task_type?" If yes, mark it for deletion.
3. Use description / summary / feature_type / metric value as available, but do not rely on a single signal blindly.
4. Examples of reasons you MIGHT delete a column (only if YOU judge them true in this case):
   - irrelevant to the prediction goal
   - no usable signal (e.g. NaN association / no overlap)
   - near-duplicate of a better column already kept
   - join-key-like identifier that should not be used as a predictive feature
5. After deletions, the remaining columns are what you keep as selected_augment_columns.

OUTPUT:
Return ONLY valid JSON (no markdown, no extra text):
{
  "dropped_columns": ["col_unneeded_1", "col_unneeded_2", "..."],
  "selected_augment_columns": ["col_kept_1", "col_kept_2", "..."],
  "reasoning": "Explain which columns you deleted as unnecessary and why; then briefly note what remains."
}

Consistency requirements:
- dropped_columns UNION selected_augment_columns must cover the input candidate feature names (no silent omissions).
- dropped_columns and selected_augment_columns must be disjoint.
